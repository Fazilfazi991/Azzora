# Authoritative backup candidate — not deployed

The existing encrypted business-only v1 archive omits database-level actor IDs and audit rows. The source candidate adds a separately versioned Owner/AAL2/service-role-only RPC that captures a company-scoped canonical snapshot plus journal actors, snapshot capturers and timestamps, audit events, idempotency receipts, membership roles/capabilities and project assignments in one PostgreSQL statement snapshot. The Owner-authorized backend encrypts the verified result in an AES-256-GCM envelope; missing RPC, revoked access, unexpected scope, incomplete journal/snapshot provenance, credential-like metadata or missing key fails closed. The production RPC is not callable by anonymous or ordinary authenticated roles. No cloud migration or real-data capture was performed.

The envelope remains `azzora-encrypted-business-backup-v1`; its decrypted payload uses `azzora-authoritative-production-backup-v2` containing the previously validated production business archive and provenance. Existing v1 business-only archives remain readable by the prior offline verifier and are explicitly reported as **not** restoring audit identity. V2 isolated rehearsal restores original journal and snapshot actors, audit-event rows and idempotency receipts against banned/unconfirmed placeholder Auth IDs, never real login credentials or sessions. It does not restore actual Auth identities, memberships or permissions. Memberships and project assignments are included for separate owner-reviewed reprovisioning only.

Authentication audit events already store provider-session IDs and session-token hashes in generic entity/request fields; recovery audit events may store recovery-token hashes in request fields. The SQL capture intentionally replaces those identifiers with `[redacted]`, while retaining event ID, actor, action, time and metadata. Therefore even v2 intentionally does not preserve these sensitive values exactly. No password, password hash, MFA factor, recovery code, token, session row or cookie is intentionally captured. Credential-like JSON keys are rejected, but structured key filtering is not proof that an arbitrary free-text field contains no secret; independent security review and data classification are mandatory before accepting real data.

The migration was created locally with Supabase CLI and added to the reviewed migration manifest. The candidate requires independent review, production RPC/ACL and cross-company tests, real-project deployment configuration, storage/retention, operating-key custody, monitored scheduled backups and a verified isolated infrastructure/Auth/Storage recovery before real use. Encryption alone and an in-memory fixture restore are not a production backup service. Real financial posting and real-document AI remain disabled.
