# Fictional staging v2 recovery candidate

The existing Owner **Download Backup** button calls `/api/staging/manager/backup/encrypted`. This candidate changes that route to request a single owner/MFA-protected fictional-staging database snapshot and encrypt an `azzora-authoritative-staging-backup-v2` payload within the existing `azzora-encrypted-business-backup-v1` AES-GCM envelope. The separate `staging_owner_backup` migration requires the synthetic staging guard, active Owner/AAL2/manager session and `access.manage`; only `service_role` may execute it. It is additive and does not modify existing functions or production migrations. No SQL has been applied to hosted staging by this change.

The v2 payload includes fictional business data and originals plus journal/snapshot actors, audit events, command receipts and role/project-assignment metadata. Session audit entity/request identifiers are redacted. The backend fails closed if the key or new RPC is unavailable, if authorization is revoked or MFA becomes stale during capture, if business/provenance inventories disagree, or if credential-like JSON keys are detected. The original plaintext staging export remains separate; the download button never silently falls back to it. Key-name filtering cannot certify that arbitrary free text contains no secret.

The offline rehearsal recognizes the staging v2 format and restores business data, original file bytes, original historical actor references, snapshots, audit events and receipts into a new in-memory PGlite instance. It creates disabled placeholder identities only. Its proof continues to state `identityUsersRestored: false`, `membershipsRestored: false` and `infrastructureBackupVerified: false`; v2 role metadata is review material, not authority to restore grants. The existing v1 staging archive and production archive verifier remain available.

The isolated staging database test explicitly denies non-Owner Manager backup, excludes a foreign project's marker, checks service-role-only ACL and session invalidation, and confirms session token and provider session IDs are absent. A separate end-to-end handler test downloads the encrypted v2 result, verifies it, restores it, and demonstrates manual **synthetic-only PGlite** user reprovisioning: an archived banned placeholder cannot sign in, a newly created Owner needs a verified synthetic MFA-factor record for an AAL2 backend session, and revocation blocks subsequent reads. This is a database-contract test; it does not implement or prove real Supabase Auth user creation, a real TOTP login, restoration of live permissions, or production recovery.

Before hosted use, security review and exact-project approval are required, then this one reviewed migration must be applied only to the authorized fictional staging project `hkhomrrvxtcxnxvdlkoh`, followed by a new protected Preview and end-to-end download/restore. Production and the existing stable live aliases remain untouched. No automatic import or real financial posting is enabled.
