# Accountant portal functional integration map — design gate

**Audited source:** `968b58e01cb4f723361c67a9e31d62be2858b58b` in the isolated Accountant design worktree, 21 October 2026. This is a read-only code audit for the owner's visual and architecture approval gate. It does not assert that the proposed separate portal, secure login, live ledger posting, or the future APIs exist. No application source was changed for this map.

## Status vocabulary and current authority

| Label | Meaning in this audit |
| --- | --- |
| **Domain-tested** | A pure rule/selector and its unit tests exist. It does not imply an authorized transaction UI. |
| **Persisted** | An existing CRM record is stored under `azzora-demo-v1` in this browser. It is not shared or secure storage. |
| **UI-connected** | A current Manager CRM form, command or read view uses the record. This is not yet the separate Accountant Portal. |
| **Synthetic-only** | Fixture or marked demo state; no real CRM journal is posted from it. |
| **Policy-blocked** | An owner accounting/approval decision in `DECISION-REGISTER.md` is unresolved. |
| **Backend-blocked** | Trusted identity, shared persistence, authorization and atomic multi-user APIs do not exist. |

The authoritative **commercial documents** are `Database.invoices`, `payments`, `expenses`, and `contracts` in [`src/domain/model.ts`](../../src/domain/model.ts), with `saveInvoice`, `issueInvoice`, `postPayment`, `reversePayment`, and `saveExpense` in [`src/commercial/repository.ts`](../../src/commercial/repository.ts). The current Manager `Accounts` UI uses these commands through `useStore().mutate` in [`src/commercial/Accounts.tsx`](../../src/commercial/Accounts.tsx) and [`src/commercial/Registers.tsx`](../../src/commercial/Registers.tsx). Issued invoice snapshots and accepted quotation/contract history must remain immutable.

The authoritative **procurement documents** are `Database.operations.bills`, `supplierPayments`, `credits`, `refunds`, orders and deliveries in [`src/operations/model.ts`](../../src/operations/model.ts). [`recordBill`](../../src/operations/repository.ts) creates one issued `SupplierBill` **and** its linked `db.expenses` project cost with `supplierBillId`; `paySupplier` and `reverseSupplierPayment` control its payments. [`src/operations/Procurement.tsx`](../../src/operations/Procurement.tsx) already exposes these commands in the Manager CRM. The linked expense is a projection/cost companion, never a second independently posted cost. Credit and refund commands are likewise in the operations repository.

[`src/finance/settlement.ts`](../../src/finance/settlement.ts) provides tested, pure explicit multi-document allocation, reversal, outstanding and due-date aging rules in integer fils. [`src/finance/document-adapters.ts`](../../src/finance/document-adapters.ts) projects **existing** single-invoice receipts and single-bill supplier payments into that model for read-only aging. Its `previewCustomerReceipt` and `previewSupplierPayment` validate proposed allocations only; neither persists them. The actual legacy write commands still accept one invoice or bill per payment. [`src/accounting/legacy-ar-ap.ts`](../../src/accounting/legacy-ar-ap.ts) provides the current read-only UI bridge. Cancellation dates missing from legacy records limit historical as-of reconstruction and must be surfaced, not guessed.

The journal core and report selectors in [`src/accounting`](../../src/accounting) are domain-tested. `Database.finance` is optional and may be saved **only** when explicitly marked `financeFixture.mode === "synthetic-demo"`; [`src/accounting/persistence.ts`](../../src/accounting/persistence.ts) rejects real CRM source IDs and enforces append-only synthetic journal/audit history. The hosted in-memory scenario in `client-demo.ts` is also synthetic-only. No source document command automatically posts a real journal. The current `AccountantWorkspace` mixes browser-record AR/AP with synthetic journals in one Manager-sidebar route; it is the rejected UI, not evidence of a live accountant system.

## Proposed command/query seam (no APIs exist yet)

After the owner approves the identity/backend and accounting policies, the Accountant shell should consume a **single trusted command/query boundary**. The names below describe contracts to design and test, not implemented endpoints:

| Proposed API family | Authoritative source and atomic behavior |
| --- | --- |
| `GET /api/accountant/me`, session/logout; scoped finance permission check | Server-verified identity, active session and role/resource membership on every read/write. No frontend role switch is an authorization gate. |
| `GET/POST /api/finance/invoices`, `issue`, `cancel`, `convert-proforma` | Canonical commercial invoice IDs/immutable snapshots, unique type-specific numbering and accepted-quotation links; one authorized command adapter around existing invariants. |
| `GET/POST /api/finance/bills`, `cancel` | Canonical procurement PO/delivery/bill ID and its **one** linked cost; source-event posting and audit in the same database transaction. |
| `GET/POST /api/finance/receipts`, `payments`, `reverse` | Canonical receipt/supplier-payment header, explicit allocation events, bank/cash account, source journal, unique idempotency key and reversal event in one transaction. Legacy `Payment.invoiceId`/`SupplierPayment.billId` remain readable. |
| `GET/POST /api/finance/expense-submissions`, `submit`, `review`, `approve`, `reject` | Review state and receipt metadata; approval invokes exactly one canonical cost/posting transition under B01/B02. Supplier-bill costs are excluded from this manual path. |
| `GET/POST /api/finance/custody`, `transfer`, `purchase`, `reconcile` | Approved bank/cash/staff holder scope. Transfer never creates P&L cost; purchase points to exactly one cost source. |
| `GET /api/finance/aging`, `journals`, `ledger`, `trial-balance`, `profit-loss`, `balance-sheet`, `reports` | Read-only selectors over authorized documents and **posted** journals; the same date/cutover and account mappings drive every view. Query results include source IDs, limitations and reconciliation state. |
| `POST /api/finance/journal-adjustments`, `reverse`, `period-lock`; finance settings | Restricted override with reason, period lock, source-action uniqueness, version check and immutable audit; only after explicit policy grants. |

The server transaction must validate an authenticated actor and resource scope **before** reading sensitive data; validate current document version and open period; apply the one canonical document command; append allocations/custody and a balanced source journal using unique posting keys; append actor/time/reason audit; and commit or roll back together. Read models may be rebuilt, but never become a parallel write store. The existing `Store.mutate` clone/save gives local browser atomicity for a single tab only; it is not a concurrency or security substitute.

## Invariants and unresolved gates

1. Money is AED integer fils in pure accounting/settlement rules. Every allocation is positive, explicitly selected, same party/side, no more than header or document outstanding. Partial payment does **not** reset the original due-date age; unallocated advances require B08 treatment.
2. Draft invoices may change; issued invoice, accepted quotation, contract, purchase order, supplier bill, credit note and historical PDF snapshots may not be silently rewritten. Corrections use controlled cancellation, credit/refund or reversal events. Legacy records retain their IDs and `azzora-demo-v1` compatibility.
3. Journal debits equal credits in fils, lines have exactly one nonzero side, account is postable, posting date belongs to exactly one open period, and `(source kind, source ID, source action)` plus posting key are unique. Reversal is a new counter-entry. Reports derive from these posted rows only.
4. A supplier bill creates its linked cost once. A paid expense and a custody purchase reference that cost rather than creating another cost. Internal bank-to-cash or Thomas cash transfer is an asset movement, never project expense or revenue.
5. Proformas are not ordinary AR/revenue/output-VAT invoices. Tax and Normal invoice treatment needs B05; quotation and contract totals are not financial-statement revenue without B04. Price variation requires stable SKU and normalized unit/currency/tax basis.
6. Browser-local records are not automatically imported to a shared database. Export and checksum original bytes, stage a read-only reconciliation, obtain signed B10 cutover/opening balances, retain rollback and exceptions, then authorize a separate production migration. A separate portal route/login prototype must state that real security is blocked until B11.

**Exact owner decisions outstanding:** B01 posting/override authority and limits; B02 expense approvers and self-approval; B03 actual receipt/document extraction scope; B04 accrual/cash and revenue recognition; B05 VAT/TRN, invoice types and tax treatment; B06 project versus company overhead allocation; B07 staff cash-holder visibility/permissions; B08 proforma advances; B09 historical PDF import mode; B10 opening balances/legacy AR-AP cutover; B11 trusted identity, backend, storage and attachment architecture; B12 currency/FX. These are recorded in [`DECISION-REGISTER.md`](DECISION-REGISTER.md). The proposed permission matrix in `src/accounting/permissions.ts` is **not enforcement**.

**Manager-side access is also gated.** The Manager sidebar currently exposes `Accounts`, `Reports`, procurement payment actions and the rejected `Accountant Preview`. Removing the preview from Manager navigation is a UI task, but keeping Manager financial forms/reports unrestricted would still violate the proposed role boundary. Until B01/B11 define and enforce per-role command/query permissions, the local prototype must avoid any claim that a Manager cannot reach accountant data by URL or call a finance action. Existing operational users' approved workflows should be preserved while access is specified and tested.

**Verification scope of this document:** source and test inspection only. No tests or browser runs were performed for this audit; the prior Checkpoint 3 test counts are historical evidence, not fresh results for the redesigned portal.
